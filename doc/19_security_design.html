1. 秘密情報

対象設計
Gemini APIキーFrontend input→Backend→Geminiのみ。環境変数/DB/localStorage/sessionStorageへ保存しない
DBパスワードRender環境変数DB_PASSWORDから注入
ソース管理.env実値や秘密値をコミットしない前提

2. SQL安全性

  • 動的テーブル名はUUID生成のみ
  • SQL識別子利用前に receipt_[0-9a-f]{32} を検証
  • 抽出文字列はPreparedStatement/parameter bindingでINSERT
  • 一覧時もinformation_schema結果をsafe patternで再フィルタ

3. ファイル安全性

  • BackendはJPEG/PNG Content-Typeと5MBを検証
  • Frontendは画像signatureを確認
  • ZIP暗号化・非画像・未知圧縮方式を拒否
  • ZIP内ディレクトリは無視

4. Web境界

  • /api/receipts/** はADMINロールのサーバーセッションを必須とし、未認証は401、権限不足は403
  • /api/health はRenderヘルスチェック用に公開
  • 管理画面はBackendの同一オリジンで配信し、セッションCookieを利用
  • ログイン、ログアウト、解析、保存、削除など状態変更にはCSRFトークンを要求
  • CORS、Referrer、画面非表示を認証の代替にしない
  • 本番ではHTTPSとSecure/HttpOnly/SameSite=Lax Cookieを使用

5. 管理者認証

管理者ユーザーIDとBCryptパスワードハッシュは ADMIN_USERNAME と ADMIN_PASSWORD_HASH の環境変数で設定します。本番用の既定認証情報はなく、設定が欠けるとBackendは起動しません。ログイン成功時にサーバーセッションを作成し、ログアウト時に無効化します。認証情報はHTML、JavaScript、公開リポジトリ、ログに記録しません。

6. ログ・エラー

  • Gemini失敗ログにはmodel / mimeType / imageBytes / exception class / messageを記録
  • アプリコード上はactive API keyをログへ出していない
  • 利用者には内部例外詳細をそのまま返さず共通メッセージへ変換

7. リスクと対策候補

リスク現状推奨
公開APIの無認証利用receipt APIはセッション認証済み管理者に限定rate limit等を必要に応じ追加
ZIP bomb / 大量エントリ明示上限なしZIP総サイズ、展開総量、エントリ数上限を追加
構造化item孤立行対策済み明示DELETEとFK ON DELETE CASCADEを維持し、回帰テストを継続
AI出力誤り保存前に原文のみ確認構造化データ確認・修正UIを追加
APIキー画面保持同一ページ内で保持共有端末では保存後に「入力を消去」を運用
